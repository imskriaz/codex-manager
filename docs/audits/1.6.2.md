# 1.6.2 operation audit

Scope: the dashboard operation catalogue and settings, their browser/VS Code routes, command handlers, authorization, service boundaries, live updates, completion feedback, retry behavior and background resource lifetimes. The review assumes concurrent windows, connected PCs, slow/offline storage and clients that disconnect during a mutation. This is a release review, not a guarantee that every possible environment is defect free.

`dashboardOperationCatalogue.test.ts` checks every declared action against the runtime API catalogue and handler cases, and every dashboard setting against its handler and manifest entry (the three SQLite logging controls intentionally have no VS Code manifest entry). This detects routing omissions; it does not substitute for the behavior suites above.

## Additional audit findings fixed in 1.6.2

1. Explicit `local` actions could enter peer routing. They now execute on the current host.
2. A WebSocket refresh could complete without delivering a snapshot when the global broadcast signature was unchanged. The requester receives its response directly; other clients still receive deduplicated broadcasts.
3. A failed browser settings write could leave an optimistic checkbox/value displayed. Failure now preserves the original error and returns stored settings for recovery.
4. Large bulk reset-permission operations could outlive the browser deadline. Deadlines now include selected-account count; remote refresh-all uses that remote account count rather than the local count.
5. A busy queue lease had no scheduled retry. One bounded retry now wakes it without needing another storage event and is cancelled on disposal.
6. Session changes during a VS Code catalogue read/cooldown could wait for the 30-second safety scan. One coalesced follow-up now delivers the change, then stops.
7. Slow/disconnected browser clients could grow buffers or interrupt delivery to other clients. Browser updates now share a bounded send path and isolate a failed connection.
8. Background leases renewed SQLite every 50 ms. Yield checks retain their responsiveness while writes occur only at the normal heartbeat interval (5 seconds by default).
9. Quota recovery read accounts every 5 seconds while healthy. Storage/quota/configuration events now wake it immediately; a one-minute fallback handles missed events. A change arriving during a read receives one follow-up check.
10. Cancelling the app-path picker had no dashboard feedback. Both dashboard hosts now report the cancellation.
11. A newer cached transcript timestamp could suppress confirmed session preference/title/goal changes. Acknowledged metadata now applies independently, while newer runtime status remains protected. The browser fixture clones messages to match the real transport boundary.
12. The optional browser notification prompt could cover task comment controls on a phone. It now yields while the task panel is open, with a real pointer-interaction check.
13. A peer disconnect replaced the entire dashboard with a loading screen, unmounting maintenance state and hiding the system picker. Saved views now remain visible with remote actions disabled; Settings keeps its operation state and pauses automatic panel reopening.

14. Opening each file unnecessarily rescanned the tree, with a shared loading flag masking unrelated file failures. File reads now coalesce, use independent loading/error states and preserve editable cached content; cache entries are scoped by actual system/project rather than session. Browser read caches reuse bounded memory, coalesce disk reads, skip unchanged durable writes and fence late cache results. Browser Git/GitHub hydrate saved views while awaiting a live read; cached state cannot authorize changes.

15. Overlapping host shutdown/startup could leave the dashboard port without a listener after an initial address-in-use result. The existing heartbeat now retries at most once per 30 seconds, coalesces starts and fences late startup after shutdown. Legacy secret cleanup no longer delays opening the dashboard.

16. Automatic panel reopening now waits while file, terminal or commit drafts remain in workspace memory, including drafts in another project. Browser reconnects continue to retain the mounted view.

17. Package inspection found internal workspace completion notes included in the VSIX. Packaging now excludes them and verifies that internal instruction/goal/log files are absent.

Browser reconnect checks retain the same conversation DOM and cached session rows through disconnect and recovery. This checks the visible content remains mounted instead of replacing it with a loading screen.

## Validation and delivery

- Stable `1.6.2` build and both TypeScript checks passed. Full lint and the final draft-guard lint passed with zero errors; existing repository warnings remain.
- The final regression run passed **2,675 tests across 214 files**. Focused cache, startup-recovery and draft-guard checks also passed.
- Desktop (1440px) and mobile (390px) inspector checks passed, including delayed host replies, cached reopening, failed lazy loading, independent file errors, revision conflicts, pending saves and Git/GitHub permission fences. Mobile task-board and reconnect checks passed, retaining the conversation DOM and saved rows.
- Read-only live dashboard smoke checks passed earlier in the audit. The installed host later stopped listening on `http://127.0.0.1:39875`; final browser checks used the explicit isolated fixture mode at that same URL, without taking the port or changing production data. The running VS Code host was not reloaded.
- The VSIX passed runtime-dependency, deferred-module, archive CRC, version and build-byte checks. Internal workspace notes are excluded. The verified VSIX was installed locally as `1.6.2`; installed runtime files and lazy chunks match the archive.

No production account reset/deletion, repository mutation through Git/GitHub workspace tools, or deployment was used for verification. Destructive paths use isolated fixtures, mocks and temporary repositories; peer failures simulate multiple connections/processes rather than controlling a second physical PC. Physical sleep prevention and private-server compatibility remain dependent on the installed OS/Codex version.

The user confirmed stable `1.6.2` publication. Release artifacts are `codex-manager-1.6.2.vsix` and its SHA-256 file, attached to the GitHub Release at `v1.6.2`. Marketplace updates and deployments remain separate actions.
